## 3. ステータス上昇計算式

### 3-1. デイリーミッション
```
実際のステータス上昇値 = 基礎上昇値 × 成長倍率
```
- 基礎上昇値 = ミッション定義の主/補助ステータス値（難易度で決まる。§3-3）。
- 成長倍率 = 現在のステータス値による逓減（§5）。

### 3-2. セルフミッション
```
実際のステータス上昇値 = 基礎上昇値（時間ベース）× セルフステータス係数 × 成長倍率
```
- 基礎上昇値 = 所要時間に対応する値（§4 時間→基礎上昇値表）。
- セルフステータス係数 = 行動内容ごとの係数（§4 係数表）。
- 成長倍率 = §5。

> **注意（SP係数と別物）**: ここで使う「ステータス係数」は `GAME_LOGIC.md §1-2(b)` の「SP係数」とは**別テーブル・別値**。SP計算にはSP係数、ステータス計算にはステータス係数を用いる（`要確認`: 2種類の係数が併存する点を実装で取り違えないこと）。

## 3-3. デイリーミッションの難易度別 基礎上昇値

### 知力・筋力・活力（通常ステータス）
| 難易度 | 主ステータス | 補助ステータス |
|---|---|---|
| 低 | +0.7 | +0.2 |
| 中 | +1.0 | +0.3 |
| 高 | +1.3 | +0.4 |

- 補助ステータスは必要に応じて付与（例: 勉強→主:知力/補助:活力）。

### 社交性（魅力）
| 難易度 | 魅力上昇値 |
|---|---|
| 低 | +1.0 |
| 中 | +1.4 |
| 高 | +1.8 |

- 魅力は上げる機会が少ないため、1回あたりを高めに設定（Notion方針）。

### 反映例（Notion）
| ミッション例 | 分類 | 難易度 | ステータス反映（DB正準） |
|---|---|---|---|
| 勉強を10分する | 知力 | 中 | 知力+1.0、活力+0.3 |
| 勉強を15分する | 知力 | 高 | 知力+1.3、活力+0.4 |
| 読書を10分する | 知力 | 中 | 知力+1.0、活力+0.3 |
| 筋トレを10分する | 筋力 | 中 | 筋力+1.0、活力+0.3 |
| 筋トレを15分する | 筋力 | 高 | 筋力+1.3、活力+0.4 |
| ストレッチを5分する | 筋力 | 低 | 筋力+0.7、活力+0.2 |
| 部屋を5分整理する | 活力 | 低 | 活力+0.7 |
| 今日の振り返りを書く | 活力 | 中 | 活力+1.0、知力+0.3 |
| 友達に一言連絡する | 魅力 | 中 | 魅力+1.4 |
| 誰かに感謝を伝える | 魅力 | 中 | 魅力+1.4、活力+0.3 |

> 「モチベーション」表記は活力(vitality)、「社交性」表記は魅力(charm)に読み替え済み。

## 7. 上限値の考え方

- ステータスは **最大100 / 最低20**。上昇計算の結果、100を超えない・20を下回らないようクランプ（`要確認`: クランプはサーバー計算側で実施）。
- 成長倍率により高レンジは実質的に到達が重くなる（95〜100は0.4倍）。
- 時間ベースの基礎上昇値は120分（+4.5）で頭打ち（`GAME_LOGIC.md §7`）。
- `要確認`: 100到達後の扱い（オーバーフロー切り捨て／記録は残すがステータスは100固定）。

## 9. DB保存の前提（`user_stats` / `score_logs`）

### `user_stats` に記録する前提
- 各ユーザーの **現在のステータス値**（`intelligence` / `strength` / `vitality` / `charm`）を保持。初期値20。
- ミッション達成のたびにサーバー計算で更新（クライアント直接更新禁止・`GAME_LOGIC.md §10`）。
- **`要確認`（型整合）**: `DB_SCHEMA_V2` では `user_stats.*` は int。だが上昇値は小数（+1.0 / +0.3 / +2.8×倍率…）。
  - Notion案「整数が必要なら **10倍にして保存**」を採用するか、`numeric` に変更するか要確定（`GAME_LOGIC.md §8` と共通の `TODO`）。
  - ×10保存案の場合: 初期値=200、最大=1000 として扱い、表示時に÷10。

### `score_logs` に記録する前提
- 1回の報酬付与ごとに、ステータス増減を明細として記録（`intelligence_delta` / `strength_delta` / `vitality_delta` / `charm_delta`）。
- 併せてSP/EXP/コイン（`season_point_amount` / `exp_amount` / `coin_amount`）も同レコードで記録し、監査・再計算の元にする。
- 二重付与防止（冪等キー）と書き込みサーバー限定は `DB_SCHEMA_V2 §4` / `GAME_LOGIC.md §9-10` に従う。
- `delta` 列も小数保持問題を共有（×10 or numeric・`TODO`）。
