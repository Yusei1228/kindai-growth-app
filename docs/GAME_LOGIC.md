## 1. SP計算式

SPは **ミッション種別（daily / self / 日記）** で算出方法が異なる。

### 1-1. デイリーミッション（daily）
- **固定値**。各ミッションに定義された `SP` 値をそのまま付与する（`DAILY_MISSIONS.md` の D001〜D054 表を正とする）。
- 例: D001「勉強を10分する」= SP 80 / D002「勉強を15分する」= SP 100。
- 時間経過による増減は**しない**（デイリーは固定報酬）。

### 1-2. セルフミッション（self）

**【確定方針】SPは「計算式」を正とする。** 早見表は計算式＋丸めルールから導出される**参考表**であり、値が食い違う場合は計算式が優先。

計算手順:
```
1) 基準SP  = 時間区分の式(a) で算出（小数可）
2) 係数適用 = 基準SP × SP係数(b)（小数可）
3) 最終SP  = 「2)の値」を 5単位に丸める（5の倍数へ四捨五入）→ 整数で保存
```
- 例: 計算値 219 → 最終SP **220**（5単位丸め）。
- 例: 計算値 67.5 → 13.5×5 として四捨五入 → **70**。
- 小数計算後、**最終保存値は必ず整数**（5の倍数）。

**【確定】実行時間と報酬対象（記録は無制限／SP・EXP・ステータス報酬は1日合計300分まで）**
- セルフミッションは**回数無制限で記録**できる（6回目・10回目でも記録は残り、振り返り画面にも表示）。`mission_logs` に実測時間をそのまま残す。
- **SP/EXP/ステータスの報酬対象は「同一 `app_date` 内の合計 最大300分」まで**。300分を超えた分は**記録のみ（報酬なし）**。短い勉強を複数回に分けても、合計300分までは報酬対象。
- **分割による報酬増加を防ぐ（累積時間の差分で付与）**: 同一 `app_date`・**同一セルフ種別**の報酬計算は、ログごとに独立計算せず、**その種別の当日累積時間に対する差分**で付与する。
  - 例（勉強10分×3回）:
    - 1回目: 累計10分 → 50SP → 今回 **+50**
    - 2回目: 累計20分 → 85SP → 今回 **+35**
    - 3回目: 累計30分 → 120SP → 今回 **+35**
    - 合計 **120SP**（＝勉強30分を1回やった場合と同じ）。
  - ステータス・EXPも同様に「当日累積時間の差分」で付与する。
- 当日累積が300分に達したら、それ以降のセルフのSP/EXP/ステータスは付与しない（記録は継続）。
- **300分を超える記録は必要に応じて `mission_logs.is_suspicious`（不正検知・要確認候補）**。
- コインは時間上限とは別枠（§5）。日記は文字数ベースで別管理（§1-3）。

**(a) 時間→基準SP（区分線形式・正／300分まで対応）**
```
0〜2分    : 0
3〜10分   : 5 × t
11〜30分  : 50  + 3.5 × (t - 10)
31〜60分  : 120 + 3.3 × (t - 30)
61〜90分  : 220 + 2.7 × (t - 60)
91〜120分 : 300 + 2.7 × (t - 90)
121〜300分: 380 + 1.0 × (t - 120)   ← 低い伸び率で延長
（t = 分。t>300 は報酬対象外＝記録のみ）
```
- 121〜300分は「120分時点の基準SP（式より約380）を起点に、**1分あたり基準SP+1.0**」で延長。
  - 例: 120分 → 約380 ／ 300分 → 約 380 + 1.0×180 = **約560**。
- 300分で報酬計算上限。係数(b)適用後、最終SPは従来どおり**5単位に丸めて整数保存**。

**(b) SP係数（種別ごと・SP用）**
| セルフミッション | SP係数 | 理由（Notion） |
|---|---|---|
| ランニング | 1.05 | 運動負荷が高い |
| 筋トレ | 1.00 | 基準 |
| 勉強 | 1.00 | 基準 |
| 読書 | 0.85 | 勉強より軽め |
| 片付け | 0.75 | 生活改善系 |
| 瞑想 | 0.75 | 負荷軽め |
| ストレッチ | 0.75 | 運動補助系 |
| 日記を書く | 0.70 | 短時間向き |

**(c) SP早見表（参考）** ＝ **計算式(a)(b)＋5単位丸めから導出した参考表**（正は計算式）
| 時間 | 勉強 | 筋トレ | ランニング | 読書 | 片付け | 日記 | 瞑想 | ストレッチ |
|---|---|---|---|---|---|---|---|---|
| 3分 | 15 | 15 | 15 | 15 | 10 | 10 | 10 | 10 |
| 5分 | 25 | 25 | 25 | 20 | 20 | 20 | 20 | 20 |
| 10分 | 50 | 50 | 55 | 45 | 40 | 35 | 40 | 40 |
| 15分 | 70 | 70 | 75 | 60 | 55 | 50 | 55 | 55 |
| 30分 | 120 | 120 | 125 | 100 | 90 | 85 | 90 | 90 |
| 45分 | 170 | 170 | 180 | 145 | 130 | 120 | 130 | 130 |
| 60分 | 220 | 220 | 230 | 185 | 165 | 155 | 165 | 165 |
| 90分 | 300 | 300 | 315 | 255 | 225 | 210 | 225 | 225 |
| 120分 | 380 | 380 | 400 | 325 | 285 | 265 | 285 | 285 |

> 参考表は「標準時間の早見用」。実装は必ず計算式(a)(b)＋5単位丸めで算出し、表とズレる場合は計算式を正とする。非標準時間（例 15/45分）も同じ計算式で算出する。

### 1-3. 日記（文字数ベース・タイマー不使用）
| 条件 | 獲得SP |
|---|---|
| 0〜49字 | 0 |
| 50〜99字 | 50 |
| 100字以上 | 80 |

- **日記としてのSP/EXP付与は1日最大2回まで**。3回目以降は記録可能だがSP・EXPは付与しない。
- 日記は**時間ではなく文字数ベース**で扱う（セルフの「300分報酬枠」の時間には算入しない）。ただしセルフ全体の**記録**には含めてよい（振り返り表示対象）。
- タイマー不要。レビューは日記本文が兼ねる。
- 表示: 「あと〇〇字でボーナス獲得！」。
- 文字数の対応DB: `mission_logs.text_content`（本文）。付与回数のカウントは `app_date`（JST・朝5時基準／§4境界注記）単位でサーバー側集計により制御。

## 2. EXP計算式

- **ミッション達成EXP = そのミッションのSPと同じ値**（SPは§1で5単位丸め整数化済み）。
  - daily: 固定EXP（D001〜D054のEXP列＝SP列と同値）。
  - self: 計算式で得たSP（5単位丸め）と同値。
  - 日記: 付与されたSPと同値（0/50/80）。
- **ボーナスEXP（別途加算）**:
  - デイリー全達成ボーナス EXP **+40**（§4）。
  - 継続日数の節目ボーナス EXP（§6: 3日+10 / 7日+30 / 14日+60 / 30日+150）。
- 累計EXP → レベルは §3。
- 対応DB: `score_logs.exp_amount`、集計は `profiles.total_exp`。

## 3. レベルアップ条件

**【確定】初期状態は `profiles.level = 1` / `profiles.total_exp = 0`。**

**しきい値式（現在Lvから次Lvへ上がるための累計EXPしきい値）**
```
次Lvへのしきい値(Lv) = 50 × Lv^2 + 100 × Lv
```
- **式の意味（確定）**: `f(Lv)` は「**現在 Lv から次の Lv+1 に上がるために必要な累計 `total_exp`**」。
  - 例: `f(1) = 150` は「**Lv1 から Lv2 へ上がるための累計EXPしきい値**」。つまり `total_exp` が 150 に達したら Lv2 になる。
  - **「Lv1 到達に 150EXP 必要」という意味ではない**（Lv1 は初期状態＝total_exp 0 でスタート）。
- **判定**: `profiles.total_exp >= f(現在Lv)` になったら `level += 1`。複数レベルの繰り上がりも順次判定。

| 現在Lv | 次Lvへのしきい値 `f(Lv)`（累計total_exp） |
|---|---|
| Lv1 | 150（→Lv2） |
| Lv5 | 1,750（→Lv6） |
| Lv10 | 6,000（→Lv11） |
| Lv20 | 22,000（→Lv21） |
| Lv30 | 48,000（→Lv31） |
| Lv50 | 130,000（→Lv51） |
| Lv100 | 510,000（→Lv101） |

- **`要確認`（旧仕様との差し替え）**: 旧プロトタイプ/旧DBの `expForLevel = 80 + level*60` とは式の意味も値も異なる。**本書のしきい値式が新仕様として優先**（実装時に旧式ロジックを置換）。

## 3.5. 日付境界（`app_date`）— JST・朝5時切替（確定）

すべての「1日」判定（デイリー配布・完全達成ボーナス・継続日数・日記2回上限・セルフ300分報酬上限・コイン上限）は、以下の**アプリ論理日付 `app_date`** を単位とする。

- **基準タイムゾーンは Asia/Tokyo（JST）**。
- **朝5時切替**: 日本時間 **04:59 までは前日扱い**、**05:00 から当日扱い**。
- **定義（確定）**: `app_date = （JSTの現在時刻から5時間引いた日時）の日付`。
  - 例: JST 2026-07-07 04:30 → 5時間引く → 2026-07-06 23:30 → `app_date = 2026-07-06`（前日）。
  - 例: JST 2026-07-07 05:00 → 5時間引く → 2026-07-07 00:00 → `app_date = 2026-07-07`（当日）。
- 判定は**サーバー側**で行う（クライアント時計を信用しない）。詳細は `DAILY_MISSIONS.md §3`。

## 4. 完全達成ボーナス（デイリー全達成）

**【確定方針】デイリーミッション（1日3件）を全達成した場合のボーナス:**

| 報酬 | 値 |
|---|---|
| EXP | **+40** |
| SP | **+20** |
| コイン | **+5** |
| ステータス | **直接上昇なし** |

- **ステータスは各ミッション達成時**にカテゴリ・時間・難易度に応じて上昇させる（`STATUS_GROWTH_RULES.md`）。**完全達成ボーナスでは直接増やさない。**
- 全達成判定: `user_missions`（`mission_source='daily'`, `app_date`, `slot_no ∈ {1,2,3}` が全て `completed`）。1日1回付与。
- 対応DB: `score_logs`（`reason='daily_complete_bonus'`）＋ `profiles.total_exp` / `season_user_scores.season_point` / `profiles.coin_balance`。
- 付与はサーバー側のみ（§9・§10）。

## 5. コイン付与ルール

**【確定方針】コインは店舗特典・クーポンに直結する通貨のため、MVPでは控えめに付与する。**

| 付与トリガ | コイン | 上限 |
|---|---|---|
| デイリーミッション1件達成 | **+1** | 1日最大3件（=最大+3） |
| デイリーミッション3件完全達成 | **追加 +5** | §4のボーナス |
| セルフミッション達成 | **+1** | **1日最大 +3コインまで** |
| 7日継続 | **+10** | §6の節目ボーナス |
| 30日継続 | **+50** | §6の節目ボーナス |

- **【確定】セルフのコインは時間上限（300分）とは別枠で管理**: セルフミッション由来のコインは**1日最大 +3**。300分以上記録しても、セルフ由来コインは最大+3のまま。デイリー完全達成ボーナス（+5）や継続ボーナスとは**別枠**。
- **イベント・ランキング報酬によるコイン付与は Phase2 または別仕様**で管理（本書の対象外）。
- **コインは SP/EXP と違い店舗特典（実利益）に影響するため、サーバー側でのみ付与し、クライアントから直接更新しない**（§10で `profiles.coin_balance` は直接更新禁止列）。
- 対応DB: `profiles.coin_balance`、`score_logs.coin_amount`。
- **【用語確定】クーポン・店舗特典で使う通貨は「コイン」に統一**（`ポイント` は原則使わない）。`DB_SCHEMA_V2` の `coupons.cost_points` は**将来的に `cost_coins` へ寄せる方針**（本段階ではSQL/カラム変更はしない・名称統一方針のみ）。

## 6. 継続日数ボーナス（ストリーク）

**【確定方針】毎日倍率で増え続ける方式ではなく、「節目ボーナス」方式とする。**

| 継続日数 | EXP | SP | コイン |
|---|---|---|---|
| 3日継続 | +10 | +5 | — |
| 7日継続 | +30 | +15 | +10 |
| 14日継続 | +60 | +30 | — |
| 30日継続 | +150 | +80 | +50 |

- **継続の判定単位**: 朝5時切替後の `app_date` 単位（`DAILY_MISSIONS.md §3`）。
- **継続条件**: その `app_date` に「**デイリーミッション1件以上**」または「**セルフミッション1件以上**」を達成したら、その日を「継続」とカウント。
- 途切れたら継続日数はリセット（`profiles.streak_count`）。
- 対応DB: `profiles.streak_count`、ボーナス付与は `score_logs`（`reason='streak_bonus'`）＋ `profiles`/`season_user_scores`。
- 付与はサーバー側のみ（§9・§10）。
- `TODO`: 途切れの猶予・復活権（ストリーク保護アイテム）は本仕様では未導入（Phase2/別仕様）。31日目以降の追加節目（60/100日等）も `TODO`。

## 7. 報酬計算の上限

| 対象 | 上限（確定） | 補足 |
|---|---|---|
| セルフの記録件数 | **無制限** | 6回目・10回目でも記録は残す・振り返り表示可 |
| **セルフのSP/EXP/ステータス報酬** | **1日合計 最大300分**（`app_date`単位・累積時間の差分で付与） | 300分超は記録のみ。分割しても得にならない（§1-2） |
| セルフSP（時間） | 300分値（基準SP約560）で上限。0〜120分は式、121〜300分は+1.0/分で延長 | §1-2(a) |
| セルフ・ステータス（時間） | 300分値（基礎上昇 +5.4）で上限。121〜300分は+0.005/分で延長 | `STATUS_GROWTH_RULES §4` |
| 日記のSP/EXP | 1日**最大2回**（文字数ベース・時間枠には算入しない） | §1-3 |
| セルフのコイン | 1日**+3**まで（**時間上限とは別枠**） | §5 |
| ステータス値 | **最大100（DB保存1000）/ 最低20（DB保存200）**・初期20 | §8・`STATUS_GROWTH_RULES §7` |
| 成長倍率 | 現在値が高いほど逓減 | `STATUS_GROWTH_RULES §5` |
| デイリー配布数 | 1日**3件**（`slot_no` 1〜3） | `DAILY_MISSIONS §2` |
| デイリー全達成ボーナス | EXP+40 / SP+20 / コイン+5（1日1回） | §4 |

> 長時間努力は「記録」としては無制限に残すが、SP/EXP/ステータスが無限に増えないよう、**報酬対象は1日合計300分まで（累積差分で付与）／コインは別枠で1日+3** に上限化する。

## 8. 小数処理・丸め処理

- **SP**: 計算式で算出後、**5単位に丸めて整数保存**（§1-2）。EXP=SPのため同値。
- **ステータス**: 上昇値は小数（例 +1.0 / +0.3 / +2.8×倍率）だが、**【確定方針】10倍した整数で保存する**（`user_stats` / `score_logs` はint系のため）。
  - 例: 表示 12.3 → DB保存値 **123** ／ 表示 45.0 → DB保存値 **450**。
  - 初期値20 → 保存 **200**、最大100 → 保存 **1000**、最低20 → 保存 **200**。
  - UIでは必要に応じて **÷10** して表示。
  - `TODO`（表示のみ）: MVPの表示を「小数1桁」か「整数」かは未確定（DB保存方式は×10で確定）。
  - `要確認`（丸めタイミング）: ×10整数化する際の端数処理（各加算時に四捨五入して整数化するか、内部は高精度で保持して表示時に丸めるか）。詳細は `STATUS_GROWTH_RULES.md §9`。
- **レベル**: 累計EXP比較は整数演算。

## 9. サーバー側で計算する方針

- **SP / EXP / コイン / ステータス / レベル / 順位 / 称号解放 / 全達成ボーナスの算出と確定は、すべてサーバー側（RPC または Edge Function）で行う**（`DB_SCHEMA_V2 §S` と整合）。
- クライアントは「ミッション実行結果（mission_id / mission_source / 所要時間 / レビュー / 証跡 / 日記本文・文字数）」を**送るだけ**。計算・付与・レベル判定はサーバー。
- サーバー処理は冪等（同一実行に二重付与しない）: `user_missions.completed_counted` ＋ `score_logs` の冪等キー（`DB_SCHEMA_V2 §4/§3`）で担保。
- 記録の流れ:
  1. `mission_logs` に実行を記録。
  2. サーバーが報酬計算 → `score_logs` に増減明細を記録。
  3. `profiles`（exp/level/coin）・`user_stats`（4ステータス）・`season_user_scores`（SP/last_scored_at）を更新。

---

## 10. クライアントから直接更新しない方針

- **SP / EXP / コイン / ステータス / レベル / 順位 / 称号解放は、クライアントから直接 `update` させない**（RLSでクライアントの書き込みを禁止し、サーバー経由のみ）。
- 対象列（クライアント直接更新禁止）:
  - `profiles.total_exp` / `profiles.level` / `profiles.total_score` / `profiles.coin_balance`
  - `user_stats.intelligence` / `strength` / `vitality` / `charm`
  - `season_user_scores.season_point` / `today_point` / `last_scored_at` / `current_rank`
  - `score_logs.*`（insertもサーバー専用）
  - `user_titles`（称号のacquired付与はサーバー）
- 目的: ランキング・クーポン（実利益）に直結するため、スコアの真正性を構造的に担保する（自己申告での水増し防止）。

---

## 11. 達成度・レビューの扱い（報酬に使わない）

**【確定方針】MVPでは、レビュー画面の達成度・自己評価を報酬計算に使わない。**

- SP / EXP / コイン / ステータスの計算に、達成度（★評価等）や自己評価は**一切反映しない**。
- 理由:
  - 自己申告のため不正しやすい。
  - SP/ランキング/店舗特典（実利益）に影響するため危険。
  - MVPはシンプルな計算（時間・難易度・カテゴリのみ）にした方が安全・堅牢。
- **達成度・レビュー文は「振り返り・自己分析・将来のAIコーチ用データ」として記録**する（報酬には使わない）。
  - 記録先: `mission_logs.review_text` / `text_content`（日記は文字数のみSPに使用＝§1-3）。
- 旧プロトタイプにあった「達成度★でSP加点」は**本仕様で廃止**（実装時に除去）。
