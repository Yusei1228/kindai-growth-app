## 3. ⚠️ 仕様と矛盾

| 矛盾点 | 詳細 | 影響 |
|---|---|---|
| 自分の月間ランキング基準が他者と異なる | 他者は個別 `monthlySP`、自分は `state.user.sp`（累計）を流用 | 月間順位が実態とズレる |
| 週間SP集計と seed 初期値の不整合 | `meWeeklySP()` は直近7日ログ合計だが seed ログは1件のみ。プロフィールは Lv23/SP2350/連続45日 | 設計画像では上位なのにランキング上は最下位付近に表示 |
| streak がリセットされない | 達成日があれば +1 のみ。日が空いても減算なし | 連続日数の意味が崩壊（累計と同義） |
| デイリー報酬が "デイリー" でない | claim 後に翌日 `true` へ戻らない | 一度きりの報酬になっている |
| `challengeDaysLeft` が静的 | seed の `6` のまま減らない | チャレンジ残日数が機能しない |
| 学部のハードコード | 自分の学部が固定 `'経済学部'` | 学部別フィルタの正確性に影響 |

## 4. 🔧 本番化に必要な修正

| 優先度 | 項目 | 内容 |
|---|---|---|
| 高 | 認証基盤の導入 | 大学メール認証（Supabase Auth 等）。シングルユーザー前提を解消 |
| 高 | バックエンド / DB 移行 | localStorage から DB（Supabase 想定）へ。ユーザー・ログ・ランキングをサーバ集計化 |
| 高 | ランキング集計の統一 | 週間/月間の算出基準を全ユーザー共通化。サーバ側集計でクライアント改ざんを防止 |
| 高 | localStorage スキーマ検証・マイグレーション | `loadState()` に型/バージョン検証。`v1→v2` 移行機構（DB移行までの暫定対策含む） |
| 中 | streak の正しい判定 | 前回達成日との差分で連続/途切れを判定。ストリーク復活権など企画書要件も考慮 |
| 中 | デイリー報酬の日次リセット | 日付ベースで `dailyRewardAvailable` を毎日再付与 |
| 中 | クーポン店頭提示カウント | 店舗課金の根拠となる利用計測（来店/提示）データモデルとAPI |
| 中 | 学部・プロフィールの動的化 | ハードコード `'経済学部'` を登録データ由来に |
| 低 | 称号機能 | 企画ロードマップ（2027 Q1）に沿って実装 |
| 低 | フレンド招待・店舗レポート等 | 企画書の周辺機能を順次 |
